Build Planner data model
========================

Saved data is account-wide and stored in GravvyBuildPlanner_Data. The top-level
schemaVersion is independent of the ESO SavedVariables version so migrations can
repair or reshape existing records without changing the storage name.

Build
-----

A build contains its name, class ID, role, game update, guide author, source URL,
notes, and an ordered list of setups. Build IDs are stable and unique within the
account-wide saved data.

Setup
-----

A setup is a named variation of a build. It stores default quality, level, and
Champion Points plus equipment requirements keyed by the canonical slot names in
EquipmentSlots.lua. It also owns the setup's skill bars and character plan.
Acquisition results live in a separate table and are not copied when a build or
setup is duplicated.

Equipment requirement
---------------------

Each populated slot may store set and resolved item identity, armor or weapon
type, trait, enchantment category, quality, level, Champion Points, and a note.
Missing fields are allowed while the player is still entering a guide. Fields
that contradict the slot family are rejected. Older free-text enchantments are
kept as custom choices until the player selects a structured category.

Acquisition classification is derived from the current ESO item link, set type,
and exact collection piece. It is not stored on the requirement, so changes to
the player's collection are reflected without rewriting the build.

When more than one acquisition route is available, acquisition[slotKey] may
store the player's preferred route. This preference is separate from the gear
requirement and is discarded if it no longer names a supported route.

Owned-item matches are also kept in memory. Each equipped, backpack, or bank
item may satisfy only one slot in a setup. Exact matches are preferred before
pieces that need a trait change, enchantment, or quality upgrade.

Setup progress is calculated in memory after inventory and collection updates.
It reports ready, adjustable, and missing requirements without writing derived
counts to SavedVariables.

A two-handed weapon is stored only in frontMain or backMain with
occupiesOffHand=true. Its paired off-hand entry is cleared and cannot be filled
until the main-hand requirement changes or is removed.

Each primary slot may also have up to eight ordered alternatives. Alternatives
use the same requirement fields as the primary and must keep the same weapon
occupancy, so a fallback cannot silently turn a one-handed bar into a two-handed
bar. Clearing a primary slot clears its alternatives. The set-wide action adds
the selected replacement set to every slot using the same primary set while
retaining each slot's remaining requirements.

An owned primary or alternative satisfies the one planned slot. Inventory items
are still assigned once across the setup, and exact matches are preferred before
adjustable matches. Alternatives therefore never increase completion totals.

Skill bars
----------

Each setup has front and back skill bars. A bar contains five active-skill
positions and a sixth ultimate position. Planned skills store the ESO ability ID
plus their localized name and icon as display fallbacks. Build Planner reads base
abilities and both morphs from ESO's native skill data but never changes the
player's equipped action bars.

Character plan
--------------

Each setup records Health, Magicka, and Stamina attribute allocations with a
combined 64-point limit. Race and Mundus use ESO's numeric identifiers so their
names remain localized by the game. Curse uses a small None, Vampire, or
Werewolf value, and three free-text class skill-line fields support both regular
and subclassed guide layouts.

Shopping List export
--------------------

Shopping-list entries are derived at export time and are never saved with a
build. Missing tradeable gear is included by default. Owned gear is counted
separately and can be included explicitly; bind-on-pickup and unresolved gear
remain excluded.

Only one requirement is exported for each slot. The primary is preferred when
it can be bought; otherwise the first tradeable alternative is used. This keeps
fallback choices from becoming duplicate purchases.

Gear keeps its set, trait, and exact level rules, while listing quality remains
open so a lower-quality piece can be bought and upgraded. Planned enchantments
can be emitted as separate glyph entries. API v2 receives the whole list in one
transaction; the same specification can be encoded as SL2 when the companion
add-on is missing or outdated.

Build sharing and backup
------------------------

GBP1 codes contain one complete build. They preserve guide metadata, setup
order and defaults, equipment requirements, item links, notes, preferred
acquisition routes, ordered alternatives, skill bars, character plans, and the
selected setup.
Derived inventory matches and collection states are recalculated after import
rather than copied.

Build Planner writes format version 4 codes and continues to accept version 1,
version 2, and version 3 codes created before equipment alternatives, skill
bars, and character plans were added.

The payload is length-delimited, versioned, and checksummed. Import validates
the complete decoded build before assigning new build and setup IDs or changing
SavedVariables. A conflicting build name receives a numeric suffix.

Settings
--------

Window position, font scale, high-contrast mode, and text status indicators are
account-wide settings. Accessibility controls appear in Add-on Settings when
LibAddonMenu-2.0 is installed; default rendering does not require the library.

Deletion recovery
-----------------

The last 20 deleted builds or setups are kept in deletedActions. Undo restores
the original record and position, adjusting its name only when another record
has since taken that name. IDs are not reused.
